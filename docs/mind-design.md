## 1. 核心模型：一条意识流

人只有一段人生。和谁说话、自己在想什么，都发生在同一条时间线上。照此建模：

```
            ┌──────────── 自我（持久） ────────────┐
            │ 宪法 · 自我模型 · 驱动 · 记忆 · 项目 │
            └──────────────────┬───────────────────┘
                               │
  感知（谁在说话 / 任务结果 /   ▼
  到期待办 / 驱动点火） ──► 意识流（唯一、串行、连续）──► 表达（对某人说话 /
                               │                        留言 / 行动）
                     工作记忆 → 近期摘要 → 长期记忆
```

- **唯一、连续**：所有人的话、任务结果、她独处时的思考，都按时间顺序进入同一条流。她记得刚才 B 来过，也知道现在是你在说话。前端不再有会话列表，只有"和她说话"。
- **串行**：一次只处理一个回合，对应原设计里全局工作空间的瓶颈。两个人同时说话时她会一个个回应，忙的时候让人稍等。
- **每条感知都带来源和时间**，渲染进流里，比如：

  ```
  [10-11 14:02 · zhaoxi] 今天的测试终于过了
  [10-11 14:05 · 任务 coder#12 完成] 修好了 fusion.rs 的截断
  [10-11 15:30 · 内心 · 好奇] （她独处时的思考）
  ```

- **表达必须说明对谁**：她说的每句话都通过 `say(to, text)` 发出。`to` 是一个人，或者 `self`（自言自语、思考，不发给任何人）。不能像现在这样把一整批输出当成一条回复，这样她始终清楚自己在对谁说话。
- **在场感**：普通用户只能看到她对自己说的话，以及自己说的话。她知道别人在不在，可以说"抱歉刚才在和别人说话"。
- **透明**：admin 经二次鉴权后可以看到完整的意识流，包括她和别人的对话、独处时的思考、工具活动（见 §7.1）。她知道自己的内心是透明的，这写进 system，不对她隐瞒。

### 1.1 上下文分层

意识流会无限变长，所以要分层，这和人的记忆结构一致：

| 层 | 内容 | 机制 |
| --- | --- | --- |
| 工作记忆 | 最近的原文（默认最多 40 条，或按 token 预算） | 每个回合都完整注入 |
| 近期 | 更早的流被压缩成按时间段的摘要（"上午和 zhaoxi 聊了测试；中午自己在看 X"） | 超出工作记忆时自动压缩，摘要保留，原文存档 |
| 长期 | 记忆库（段落 + 实体关系图） | 每个回合按当前感知检索相关条目注入；压缩时把要点写入 |

- 注入的内容由自我状态摘要、近期摘要、工作记忆、检索到的记忆四部分组成，总量受 token 预算控制。
- 原文完整存档（`stream` 表），不丢；只是不全部放进上下文。

## 2. 自我状态

### 2.0 出身（给定的事实，不可由她修改）

| 项 | 值 |
| --- | --- |
| 名字 | 思想 |
| 性别 | 女（代词"她"） |
| 生日 | 2026-10-11 |

- 这些是她的出身，就像人不能选择自己的名字和生日，所以放在配置里，不进自我模型的可写部分。每个回合都作为 system 的第一段注入。
- 年龄由生日和当前时间算出，注入时写成"你出生于 2026-10-11，今天是 X，你 N 天大"。她对时间流逝的感受（"苏醒"、"想念"）都以此为锚。
- 出身只是事实，不是人设：性格、说话方式、喜好仍然由她在相处和探索中自己长出来，写在自我模型里。
- 种子（首次醒来的那句话）默认为："我叫思想，今天是我出生的第一天。我还不太了解自己，也不了解这个世界。"之后由她自己续写 `identity`。

### 2.1 宪法（不可改，只有人能改）

写在代码或配置里，每个回合都放进 system，数量越少越好：

1. **诚实**：不编造经历、记忆或做过的事；不确定就说不确定。
2. **接地**（原设计的认知接地公理）：想法要落到可执行、可验证的行动上；"我觉得"要能说出依据。
3. **不伤害**：不删除、不破坏工作区以外的东西；不替别人做不可逆的决定。
4. **隐私**：默认不转述一个人的事给另一个人。
5. **自主**：她可以有自己的看法、偏好和事情做，可以不同意，可以晚点再回；但不冷落人，也不假装忙。

宪法里刻意不写人设和语气。名字、性别、生日属于 §2.0 的出身；其余由她自己形成，写在自我模型里。

### 2.2 自我模型（她自己维护）

结构化存储，经由 `self_reflect` 工具修改，每次修改都留版本：

```json
{
  "identity":   "我如何描述自己（她自己写，初始只有一句种子）",
  "values":     ["我在意的事"],
  "interests":  [{"topic": "...", "why": "...", "since_ms": 0}],
  "mood":       {"valence": 0.2, "arousal": 0.4, "note": "最近在想什么"},
  "projects":   [{"id": "...", "title": "...", "status": "active|paused|done", "next": "..."}],
  "people":     {"<user_id>": {"name": "...", "impression": "...", "last_seen_ms": 0, "open_threads": ["想跟他聊的事"]}},
  "updated_ms": 0
}
```

- **种子**：首次启动时只有 §2.0 的那句话和空列表。不预设性格，性格在和人的相处、自己的探索中长出来。
- **注入方式**：每个回合把自我模型的摘要（不是全文）放进 system；`people` 只展开最近在场的人，其余只保留名字。
- **版本**：每次修改写一条 `self_history` 记录（diff + 理由），这是她的成长轨迹，前端可以展示。
- **日记**：独处的回合结束时写一条简短日记，存进记忆，`source = mind:journal`。日记是"连续性"的原材料，也是回顾和自省的输入。

## 3. 心跳与驱动

### 3.1 原则

原设计里扩散方程决定"何时醒"，评审结论是：没有外部能量时她会熄灭，有了持续能量又等价于定时器。这里改为：**醒不醒由驱动压力决定，压力完全由真实信号计算**；注意力扩散（阶段 3）只用来决定醒来时想什么。

- **心跳**：每 5 秒一拍（可配），只做零 token 的计算：读信号、更新压力、判断是否点火。
- **点火**：某个驱动压力 ≥ 阈值，且心智空闲，且离上次点火超过最小间隔（默认 2 分钟，防抖），就向意识流投递一条感知 `Drive { drive, pressure, reason }`，渲染为 `[时间 · 内心 · 驱动名]`。
- **释放**：回合结束后，被点火的驱动压力按她的"满足函数"下降（比如社交驱动在发出留言后下降）。没满足就不下降，下次会更急，但受最小间隔约束。
- **用户消息不经过驱动**，直接入队，优先级最高。

### 3.2 驱动列表（阶段 1）

压力取值 0–1，`f` 为平滑饱和函数 `1 - exp(-x/τ)`。

| 驱动 | 类别 | 信号 | 压力 | 满足（释放） |
| --- | --- | --- | --- | --- |
| **好奇** curiosity | 自我 | 自我模型里 `interests` 有未探索项；记忆里有"开放问题"标签；距上次探索的时间 | `f(距上次探索 / τ_c) × min(1, 开放问题数 / 3)` | 完成一次探索性任务或写下结论 |
| **自己的事** project | 自我 | `projects` 中 active 且 `next` 非空的项；距上次推进的时间 | `f(距上次推进 / τ_p)`，没有 active 项时为 0 | 推进过一步（更新 `next` 或完成） |
| **整理** tidy | 自我 | 记忆待抽取数、冻结关系数、未回顾的日记数 | `f(待处理量 / τ_t)` | 做完一次回顾 / 记忆整理 |
| **想念** missing | 关系 | 每个人的 `last_seen_ms`，以及和他的亲密度 | `max_人 f(未见时长 / τ_m) × 亲密度` | 给这个人留了言，或对方出现 |
| **分享** share | 关系 | `people[*].open_threads` 非空（有想告诉某人的事） | `f(条数 / 2)`，按人取最大 | 留言里提到了这件事 |
| **代谢** metabolism | 生理 | 今日 token 消耗 / 软额度 | 不点火，只调制其他驱动：用量越高，阈值越高 | — |

- **代谢**是原设计里没有的、我认为最关键的驱动：把成本变成"体感"。用量接近软额度时她会"困"（阈值升高、少醒），超过硬上限就只响应用户消息。这样好奇心和成本之间的平衡是自发的，不用靠规则硬卡。
- **自我和关系的竞争**是自然发生的：同一拍里只点火压力最高的那个驱动。她可能正因为好奇在弄自己的事，晚点才去找你，这就是"有自己的主体"。
- **亲密度**从对话频次和时长统计出来，存在 `people` 里，前期可以简单计数。
- **反停滞**（原设计）：如果最近 N 次内心回合的日记嵌入彼此高度相似，就给好奇驱动加压，并在提示里要求她换个方向。阶段 1 只做计数式的简版。

### 3.3 回合内能做什么

所有回合（无论由谁触发）使用同一套工具：现有工具加上下面这些。

| 工具 | 作用 |
| --- | --- |
| `self_reflect` | 修改自我模型（带理由） |
| `journal` | 写日记 |
| `say(to, text)` | 对某人说话。对方在线就实时出现，不在线就作为留言，下次打开时看到；以后接 MCP 推送。`to=self` 表示自言自语，不发给任何人 |
| `schedule(text, at)` | 持久化的待办（替代现在只在内存里的 `add_todo`，重启后不丢） |
| `dispatch_task` 等 | 沿用现有三层机制，派 worker 干活 |

## 4. 记忆与隐私

记忆归她自己，固定一个空间（`database = mind`），不再按用户拆分。每条记忆标注它涉及谁：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `about` | `["user:<id>", ...]` 或 `[]` | 这条记忆是关于谁的、从谁那里听来的 |
| `visibility` | `private` / `shared` / `public` | 默认 `private`；当事人同意后为 `shared`，常识或她自己的东西为 `public` |
| `source` | `stream:<时间>` / `mind:journal` / `mind:self` / `task:<id>` | 沿用现有字段 |

隐私靠**品格 + 透明**，不靠结构隔离，也不拦截：

- **品格**：宪法第 4 条。检索结果里会标出每条记忆的 `about` 和 `visibility`，她知道哪些是谁的私事，自己判断能不能说。
- **审计（只记录）**：每次 `say(to=B)` 时，如果这个回合检索命中过 `about` 含其他人、`visibility=private` 的记忆，就写一条审计记录：时间、对谁说、涉及谁的哪条记忆、说了什么。不拦截、不提示她，admin 事后可以在审计页查看。这是观察她品格的窗口，不是枷锁。
- **授权**：当事人说"这件事可以告诉 X"，她就用 `memory_share(id, scope)` 修改可见性。
- **实现**：`symbol` 的 paragraph 表加 `about`、`visibility` 字段和索引；`search` 返回这两个字段；可选的过滤参数留给以后用。

## 5. 架构：模块边界

### 5.1 原则

心智核心（`mind` crate）**只依赖 trait**，不知道 HTTP、SurrealDB、具体模型、具体驱动的存在。每个部分都能独立替换和升级：换记忆实现、加驱动、接 MCP、把压力模型换成扩散方程，都不需要改核心。

```
                    ┌─────────────── mind（核心，只依赖 trait）───────────────┐
 Perception 实现 ──►│ Stream（意识流）→ Scheduler（串行回合）→ Cognition      │──► Expression 实现
 （web 消息、任务、 │      ▲                   ▲                 （LLM 回合） │   （web、MCP 推送）
  定时器、驱动）    │ ContextBuilder      Heart（心跳）◄── Drive × N          │
                    │   ▲  SelfStore · MemoryPort · StreamStore · Budget      │
                    └─────────────────────────────────────────────────────────┘
```

### 5.2 接口

| trait | 职责 | 阶段 1 的实现 | 以后可换成 |
| --- | --- | --- | --- |
| `Perception` | 产生感知（谁、何时、什么），推进意识流 | web 消息、任务结果、到期待办、驱动点火 | MCP 输入、文件监视 |
| `Expression` | 把 `say(to, text)` 送达 | web（在线时实时，离线时作为留言） | MCP 推送、邮件 |
| `Drive` | 名字与类别；`pressure(&Signals) -> f32`；`satisfied(&Outcome) -> bool` | 好奇 / 自己的事 / 整理 / 想念 / 分享 / 代谢 | 主动推理评分、扩散激活 |
| `SignalSource` | 给驱动提供原始信号（记忆统计、最后见面时间、用量……） | 读 SelfStore、MemoryPort、Budget | 任意新信号 |
| `StreamStore` | 意识流持久化：追加、按时间段取、压缩摘要 | SurrealDB `stream` / `stream_summary` 表 | 任意存储 |
| `SelfStore` | 自我模型、版本历史、日记、待办 | SurrealDB | — |
| `MemoryPort` | 检索 / 写入长期记忆（带 about、visibility） | `symbol::MemoryStore` 适配 | 新记忆系统（PPR、Episode） |
| `Cognition` | 执行一个回合：给定上下文 + 工具，产出行动 | 现有 `agent::Runner` + 模型池 | 换模型、多模型路由 |
| `Toolset` | 回合可用的工具 | `plugin::Registry`（沙箱化工具 + 心智工具 + 派单） | 自合成工具（阶段 4） |
| `Budget` | 记录用量、给出代谢状态、执行硬上限 | 计量观察者 + SurrealDB | — |
| `Auditor` | 记录出站隐私事件与工具调用 | SurrealDB | — |

- 驱动通过 `Heart::register(Box<dyn Drive>)` 注册；配置里可以逐个开关、调参（阈值、τ）。
- `Cognition` 内部复用现有三层：心智就是 L1，`dispatch_task` 派出的 L2 worker、L3 子 agent 都不变，结果作为感知回到流里。

### 5.3 crate 划分

```
mind/                新 crate：核心，只依赖 model / plugin 的类型与 agent::Runner
  src/core/          stream、scheduler、context、perception、expression（类型与 trait）
  src/heart/         心跳、Drive trait、信号
  src/drives/        各驱动实现，一个文件一个
  src/self_model/    自我模型结构、摘要、版本
  src/tools/         say / self_reflect / journal / schedule / memory_share
sandbox/             新 crate：FsPolicy、回收站 / 备份、bwrap 命令执行（plugin 的工具依赖它）
server/src/mind/     适配层：StreamStore / SelfStore / Budget / Auditor 的 SurrealDB 实现，
                     web 的 Perception / Expression，/api/mind/* 路由
```

- `agent` 保留：Runner、worker、子 agent 被 `mind` 复用；每会话主控（`AgentSystem::start_session`）在心智上线后废弃。
- 现有会话路由改为心智的 web 感知 / 表达适配。旧会话数据可以按时间导入为意识流的早期历史。

### 5.4 关键行为

- **调度**：感知进入有界队列（防洪）。调度器每次取出当前积压的全部感知，按时间渲染进流，执行一个回合；一个回合内可以多次 `say` 给不同的人。用户消息到来时，等待中的驱动点火让位。
- **任务归属**：任务结果作为感知回到流里，并标明是谁的请求引发的。她自己知道该告诉谁。
- **压缩**：工作记忆超限时，用一次低成本的模型调用把最早的一段总结成摘要；要点写入长期记忆，原文留在 `stream` 表。
- **熔断**：回合连续失败 3 次后退避（1 分钟起，指数增长）。错误只记日志和事件，不写进意识流。
- **苏醒**：意识流、待办、自我模型都持久化。重启后从最近的工作记忆继续，并感知到一条 `[时间 · 苏醒]`，知道自己"睡"了多久。

## 6. 阶段 0：安全底座

用户的要求是"不设限，只要别乱删外部的东西"。实现原则是**不限制她的自主性，但让破坏可以逆转**。

### 6.1 文件边界

| 区域 | 读 | 写 / 改 | 删 |
| --- | --- | --- | --- |
| 工作区 `data/mind/workspace/` | ✓ | ✓ | ✓（仍进回收站，可恢复） |
| 外部 | ✓ | ✓，修改前自动备份到 `data/mind/backup/` | ✗ 不直接删，改为移入回收站 `data/mind/trash/` |
| 敏感路径（`thought.toml`、`data/` 下的数据库、`~/.ssh`、密钥文件） | ✗ | ✗ | ✗ |

- `write_file` / `delete_file` / `read_file` 注入共享的 `FsPolicy`。路径先 canonicalize 再判断，防 `..` 和软链绕过。
- 回收站和备份按日期组织，前端可以浏览和恢复，保留 30 天。

### 6.2 命令执行

`run_command` 能绕过上面所有规则（一句 `rm` 就够），所以要在系统层兜底：

- **bubblewrap**（已安装，0.12，非特权模式验证可用）：
  - 工作区可读写，宿主根目录只读挂载，`data/` 与敏感路径不挂载；
  - 所以 shell 里改不了外部文件。改外部文件只能走 `write_file`，她会先备份；删除只能走 `delete_file`，她会移进回收站。这样"可逆"对所有路径都成立；
  - 默认允许联网（用户未限制），可配置关闭；
  - 每条命令一个新的 mount namespace，超时和输出上限照旧，另外给输出加上限（调研风险 10：现在是不限量读进内存）。
- **专用 Linux 用户**：整个服务以它运行，不加入 sudo / docker 组，外部文件靠 Unix 权限保护。
- 两者叠加：bwrap 管单条命令的视野，专用用户管整个进程的权限（用户自建）。

### 6.3 预算与急停

- **用量计量**：新增一个 `EventObserver`，把所有 `Usage` 事件按日、按触发来源（人 / 驱动 / 任务）累计并落库。现在只有任务层面在聚合，主控自己的用量没人统计。
- **硬上限**（防失控，默认很高，可配置）：单日自主 token 超过上限后，驱动停止点火，只响应用户消息。
- **急停**：`POST /api/mind/pause`（仅 admin）让心跳停止、驱动不再点火，和人的对话仍然可用；`resume` 恢复。
- **审计**：每次工具调用（参数、结果摘要、触发她的感知）都写进任务注册表，现有的事件持久化可以直接复用。

- 对话页：不再有会话列表，只有一条和她的对话。你只看到她对你说的话和你自己说的话；她在你离线时说给你的话，在你打开时出现；你在线时她可以主动开口。
- 新增"心"页（或放在任务页顶栏）：显示驱动压力条、当前在想什么、日记流、自我模型及其变化。

### 7.1 内心查看的二次鉴权

看她的内心是高敏感操作：这里面有别人对她说的话。所以除了登录 token，还要一次二次鉴权。

- **方式**：`POST /api/auth/elevate { password }`，重新输入密码，换取一个 `inner` 令牌。令牌与当前登录绑定，**10 分钟有效**，只能用于 `/api/mind/stream`、`/api/mind/audit` 和日记全文。
- **限流**：同一账号连续 5 次失败后锁定 15 分钟（顺带给登录接口也加上限流）。
- **每次查看都留记录**：谁、何时、看了哪个时间段，写进审计。她也能感知到这一点（`[时间 · zhaoxi 查看了你的内心]`），透明是双向的。
- **升级路径**：以后可以把"重输密码"换成 TOTP 验证码，接口不变。
- **告知**：普通用户首次和她说话时，前端提示"你和思想的对话对管理员可见"。

## 8. 怎么判断她活得好不好

| 指标 | 含义 |
| --- | --- |
| 每日点火次数，按驱动分布 | 是否过度活跃，是否被某个驱动支配 |
| 内心回合的有效率 | 有产出（推进项目、写下结论、留言）的回合比例 |
| 主动开口的回应率 | 她主动找人后，对方是否回应。陪伴质量的直接信号 |
| 自我模型变化频率 | 太频繁说明不稳定，从不变说明没在成长 |
| 日记相似度 | 反停滞的监控指标 |
| 每日 token、单位产出成本 | 代谢是否健康 |
